# Manual v0.5.0 → v0.6.0 community migration

Prepared only: **this migration has not been executed or tested against a live MySQL server**. Startup never applies it. Review and run it manually when you approve changing your database.

## What changes

The additive script creates `trainer_public_settings` and `team_sharing` in **pokedex_app**. It does not alter existing tables, copy teams, backfill public settings, or modify users, password hashes, sessions, biographies, avatars, team members, favourites, collection entries or awards. Missing settings rows mean private; all visibility flags default to false. Public biography starts empty and is separate from the existing private biography. Team links use unique UUIDv4 identifiers generated by Express, never sequential IDs as access credentials.

Foreign keys clean up settings on user deletion and sharing rows on team deletion. Deleting a featured team clears its reference. Species IDs have the existing 1–649 bounds. Boolean CHECK constraints reject invalid flags. Featured-team ownership is checked and locked by Express inside the settings transaction; a foreign key alone cannot prove ownership.

Existing installations must already have the v0.5.0 schema. If needed, follow the earlier [v0.2.0](MIGRATION_v0.2.0.md) and [v0.5.0](MIGRATION_v0.5.0.md) migration guides in order. New installations use the updated `database/schema.sql` instead. Do not recreate an existing database.

## Workbench steps

1. Stop your Express process. Preserve `.env`, its session secret, and `uploads/avatars`. Back up **pokedex_app** with Workbench **Server → Data Export** and back up uploads separately outside the public repository. MySQL DDL is not undone by a normal transaction rollback.
2. Connect to the intended MySQL 8.0.16+ server. Inspect the selected database, current definitions, table names and original counts:

```sql
USE pokedex_app;
SELECT DATABASE();
SHOW TABLES;
SHOW CREATE TABLE users;
SHOW CREATE TABLE teams;
SELECT 'users' AS entity, COUNT(*) AS total FROM users
UNION ALL SELECT 'teams', COUNT(*) FROM teams
UNION ALL SELECT 'team_pokemon', COUNT(*) FROM team_pokemon
UNION ALL SELECT 'favorites', COUNT(*) FROM favorites
UNION ALL SELECT 'sessions', COUNT(*) FROM sessions
UNION ALL SELECT 'user_pokedex', COUNT(*) FROM user_pokedex
UNION ALL SELECT 'user_achievements', COUNT(*) FROM user_achievements;
```

3. If either new table already exists, inspect its `SHOW CREATE TABLE` first. `IF NOT EXISTS` does not repair conflicting definitions. Do not drop existing tables to resolve a conflict.
4. Open `database/migrations/v0.6.0-trainer-community.sql` in Workbench. Review its two CREATE statements and confirm it selects only **pokedex_app**. When approved, execute the script manually.
5. Inspect the new definitions and repeat the original counts before restarting Express:

```sql
SHOW CREATE TABLE trainer_public_settings;
SHOW CREATE TABLE team_sharing;
SELECT COUNT(*) AS public_profiles FROM trainer_public_settings WHERE enabled = 1;
SELECT COUNT(*) AS public_teams FROM team_sharing WHERE is_public = 1;
SELECT COUNT(*) AS invalid_featured_ownership
FROM trainer_public_settings s JOIN teams t ON t.id = s.featured_team_id
WHERE t.user_id <> s.user_id;
```

For an untouched existing installation, both public counts and invalid ownership should be zero. The original seven tables' counts should match your pre-migration observations. Do not reset flags on a database that already intentionally contains public settings.

6. Restart with `npm.cmd start`. Verify an existing account still has its private biography, avatar, teams, favourites, progress and awards. Test the [community verification flow](../COMMUNITY.md#manual-verification) with two development accounts and a logged-out browser before publishing.

Before migration, the new sharing APIs display an actionable 503; existing trainer operations and private client-side analysis remain usable. If a post-migration issue occurs, stop the app, preserve the tables/data and diagnose from the backup and definitions. Reverting application code does not require dropping the additive tables. Never run cleanup or rollback SQL automatically.
